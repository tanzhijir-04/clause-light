# 基于多阶段 Agent 的合同风险辅助审查系统设计与实现

## 摘要

针对 PDF、扫描图片等非结构化合同材料难以快速审查，且普通用户难以准确定位付款、违约、责任限制和争议解决等风险的问题，本文设计并实现了一种基于多阶段 Agent 的合同风险辅助审查系统 ClauseLight。系统采用“文档解析—条款结构化—多维度风险分析—结果聚合”的流水线架构：首先通过文档解析与 OCR 技术获得合同文本；随后利用大语言模型完成合同类型识别和条款拆分；在此基础上，将条款路由至权责对等、财务风险、知识产权、争议解决和通用风险五个分析维度，并行生成风险等级、问题说明、修改建议及相关依据；最后对不同维度的分析结果进行冲突检测、综合评分和可视化展示。系统后端采用 Python 与 FastAPI 实现，使用 SQLite 保存本地数据，并通过统一的模型网关支持兼容 OpenAI 接口的远程模型和本地模型。

本文重点介绍系统的需求分析、总体架构、关键模块设计和工程实现，并通过功能测试与脱敏合同案例对系统流程进行验证。研究结果用于说明该系统在合同风险辅助审查场景中的工程可行性。由于法律风险判断具有较强的专业性，本文不将系统输出视为法律意见，并对模型稳定性、知识库检索、人工标注和样本覆盖等局限进行讨论。

**关键词：** 合同风险审查；大语言模型；Agent；文档解析；OCR；多阶段流水线

## 1 引言

### 1.1 研究背景

合同是商业交易、劳动用工、房屋租赁和项目合作等活动中的重要法律文本。现实中的合同通常以 PDF、扫描图片或办公文档的形式保存，文本结构可能受到页面布局、扫描质量、字体和表格格式的影响。对于不具备法律专业背景的普通用户而言，在签署合同前快速识别付款周期、违约责任、单方面解除权、责任上限、知识产权归属和争议解决等条款中的潜在风险并不容易。

传统合同审查通常依赖人工逐条阅读，审查质量受人员经验、时间和合同长度影响。近年来，大语言模型在文本分类、信息抽取和自然语言生成方面表现出较强的通用能力，为合同条款解析和风险提示提供了新的技术路径。然而，直接将完整合同交给大语言模型进行一次性分析仍存在三个问题：一是长文本可能导致关键信息遗漏；二是不同风险类型混杂在同一次推理中，输出结构和判断标准不稳定；三是模型给出的结论不一定具有清晰的条款依据，难以支持用户复核。

因此，本文不将合同审查任务建模为单次问答，而是将其拆分为多个相互衔接的处理阶段。系统先把非结构化文件转换为结构化条款，再由不同风险维度的分析 Worker 分别处理，最后对分析结果进行统一聚合和展示。该方法的目标是提高系统流程的可观察性、模块可维护性和用户复核便利性。

### 1.2 研究内容

围绕合同风险辅助审查场景，本文主要完成以下工作：

（1）设计并实现文档入口模块，对文字型 PDF、图片等材料进行统一处理，并在不同解析路径之间进行降级；

（2）设计合同结构解析模块，将合同全文转换为合同类型、条款编号、条款标题、条款正文和风险维度关联关系等结构化信息；

（3）设计五维风险分析流程，将条款分别路由到权责对等、财务风险、知识产权、争议解决和通用风险 Worker，并通过异步并行方式组织分析请求；

（4）设计冲突检测、结果聚合和人工复核标记机制，使用户能够查看风险等级、问题描述、修改建议和原文依据；

（5）实现本地化数据存储、模型统一调用、异常重试和知识库检索等工程支撑功能。

### 1.3 论文组织结构

本文共分为七个部分。第一部分介绍研究背景、相关研究、研究内容和论文结构；第二部分进行需求分析并介绍系统设计目标；第三部分介绍系统总体架构和数据流程；第四部分说明系统关键模块的设计与实现；第五部分介绍测试方案和典型案例；第六部分讨论系统特点、局限和改进方向；第七部分总结全文。

### 1.4 相关研究与技术基础

大语言模型能够对合同文本进行分类、信息抽取和自然语言解释，但合同审查通常需要同时处理长文档、跨条款关系和证据定位问题。ContractNLI 将合同审查建模为文档级自然语言推理任务，要求系统判断假设与合同之间的蕴含、矛盾或未提及关系，并识别支持判断的证据片段[1]。这一思路说明，合同分析系统不能只输出整体标签，还应保留与具体条款相关的依据。

LexGLUE 将多个法律语言理解任务组织为统一基准，体现了法律文本处理任务在分类、检索、条文预测和推理等方面的多样性[2]。DocInfer 进一步研究了长文档中的证据选择问题，并在合同和其他法律文本数据集上验证了证据筛选对文档级推理的作用[3]。本文不直接复现上述基准任务，而是结合合同风险辅助审查场景，将条款结构化、风险维度分工和证据展示组织为一套工程流程。

ReAct 研究了大语言模型推理过程与外部行动交替执行的方式[4]。与完全自主的 ReAct Agent 不同，本文采用固定阶段的 Pipeline，并只在冲突条款复核时调用有限的知识和记忆工具。这种取舍主要考虑合同审查步骤相对明确、需要稳定输出和便于工程测试的特点。

对于扫描合同和图片合同，OCR 是系统进入后续语义分析的前置环节。PP-OCR 研究了面向实际场景的轻量化 OCR 系统，强调文本检测、方向处理、文本识别和计算效率之间的平衡[5]。本文使用 OCR 与文字层解析相结合的文档入口，并在文本不足或解析失败时提供降级路径。

## 2 需求分析与系统设计目标

### 2.1 功能需求

ClauseLight 的核心使用流程为：用户上传合同文件，系统完成文字识别和条款分析，最终返回风险提示和修改建议。根据该流程，系统需要满足以下功能需求。

#### 2.1.1 合同文件接入

系统应支持用户上传 PDF、图片等常见合同文件，并对文件类型和大小进行基本校验。对于包含文字层的 PDF，系统优先提取已有文本；对于扫描图片或文字提取结果不足的文件，系统调用 OCR 进行识别。解析结果应统一转换为后续模块可以处理的文本对象。

#### 2.1.2 合同结构解析

系统需要识别合同类型并拆分合同条款。每条条款至少包含条款编号、标题、正文、条款类型和相关风险维度等信息。结构化结果用于控制后续 Worker 的输入范围，减少无关文本对分析结果的干扰。

#### 2.1.3 多维度风险分析

系统将风险分析划分为五个维度：权责对等、财务风险、知识产权、争议解决和通用风险。每个维度关注不同的合同风险问题，并输出风险等级、风险类型、问题说明、不利方、严重程度、修改建议和相关依据等字段。

#### 2.1.4 结果聚合与展示

系统应对多个风险 Worker 的分析结果进行合并，统计红、黄、绿风险数量，生成综合风险分数和处理建议，并对存在不同评级的条款进行人工复核提示。前端应支持查看条款原文、风险说明、修改建议和相关法律资料。

#### 2.1.5 异常处理与本地存储

由于文档解析和大语言模型调用均可能失败，系统应提供重试、超时和降级处理。合同和分析结果默认保存在本地 SQLite 数据库中，避免将用户合同自动上传到额外的业务服务器。远程模型调用是否启用由用户配置决定。

### 2.2 非功能需求

（1）**可维护性。** 将文档解析、模型调用、条款解析、风险分析和结果聚合拆分为独立模块，便于替换模型或调整某一风险维度。

（2）**可解释性。** 系统输出应尽量绑定到具体条款，避免只返回无法追溯的总体分数。

（3）**可扩展性。** 风险维度、规则库和模型提供商应能够在不改变主要 API 的情况下扩展。

（4）**数据安全性。** API Key 不写入业务代码，合同正文不在日志中完整输出，用户可以选择本地模型或关闭同步功能。

（5）**降级可用性。** 某一解析路径、知识库检索或单个 Worker 失败时，系统应记录失败状态并尽可能保留人工复核所需的信息。

### 2.3 系统设计目标

本文将系统设计目标概括为以下三点：第一，将复杂合同分析任务拆解为可观察、可测试的处理阶段；第二，通过风险维度分工降低单次模型调用的任务复杂度；第三，将模型输出转换为面向用户的条款级风险提示，而不是仅提供不可解释的整体结论。

## 3 系统总体设计

### 3.1 总体架构

ClauseLight 采用本地优先的客户端—服务端结构。用户可以通过管理面板上传合同文件，后端服务负责文档解析、模型调用、知识库检索和结果持久化，前端负责进度展示与结果渲染。系统主要由文档入口层、Agent 编排层、知识支撑层、数据存储层和结果展示层组成。

系统的基本数据流如下：

```text
合同文件
   │
   ▼
文档解析与 OCR
   │
   ▼
合同类型识别与条款结构化
   │
   ├── 知识库与法规资料检索
   │
   ▼
五维风险 Worker 并行分析
   │
   ▼
冲突检测与二次复核
   │
   ▼
风险聚合、综合评分与建议
   │
   ▼
条款列表、原文标注和分析报告
```

后端主要使用 Python、FastAPI 和 SQLAlchemy 实现，SQLite 用于保存合同、分析结果、条款分析和知识规则等数据。大语言模型调用通过统一网关完成，以便适配不同的 OpenAI 兼容接口和本地 Ollama 模型。文档入口根据文件类型和文本提取结果选择 AnyDoc、PyMuPDF 或 PaddleOCR 等路径。

### 3.2 多阶段 Agent 流程

系统不是一个完全自主的 ReAct Agent，而是以预定义 Pipeline 为主、以有限工具调用为辅。合同风险审查的处理步骤具有相对明确的顺序，因此使用固定阶段能够使输入、输出和错误位置更容易被记录。

#### 3.2.1 Stage 1：结构解析

Stage 1 接收文档入口输出的合同全文，调用大语言模型识别合同类型并拆分条款。每个条款包含编号、类型、标题、正文和相关风险维度。`relevance` 字段用于决定该条款是否需要被某个风险 Worker 分析。

#### 3.2.2 Stage 2：并行风险分析

Stage 2 根据条款的风险维度关联关系组织五个 Worker。各 Worker 接收与自身维度相关的条款，并按照统一结构输出分析结果。系统使用异步任务并行执行不同维度的分析请求，再合并各 Worker 的结果。

#### 3.2.3 冲突复核

同一条款可能同时属于多个风险维度。例如，责任限制条款既可能涉及权责对等，也可能涉及财务风险。当同一条款出现红色和绿色评级时，系统将其标记为冲突，并触发包含其他维度意见的二次分析。冲突条款同时保留人工复核标记。

#### 3.2.4 Stage 3：结果聚合

Stage 3 接收所有 Worker 的结果，统计风险分布，生成综合风险分数、最高风险条款、简要总结和处理建议。聚合结果最终与条款结构信息合并，供前端按风险等级展示。

### 3.3 核心数据对象

系统内部主要使用以下数据对象：

（1）**DocumentResult。** 保存全文、页面信息、来源路径和平均解析置信度。

（2）**ClauseItem。** 保存条款编号、类型、标题、正文和相关风险维度。

（3）**ClauseRisk。** 保存条款风险等级、风险类型、问题说明、不利方、严重程度、修改建议和法律依据。

（4）**AnalysisResult。** 保存合同类型、综合分数、风险分布、最高风险、人工复核条款和条款级最终结果。

（5）**KnowledgeRule 与 LegalReference。** 保存可供检索的规则、法规名称、条文编号和条文内容。

## 4 关键模块设计与实现

### 4.1 文档解析与 OCR 降级

文档解析模块通过统一的 `ingest` 接口接收文件路径，并根据文件类型和已有文本质量选择处理路线。对文字型 PDF，系统优先使用文本层解析；当文本层不足或文件为图片时，系统转入 OCR 路径。OCR 结果包含全文、页面、文本块和置信度等信息。

系统在解析完成后检查全文是否为空，并记录平均置信度。当置信度低于设定阈值时，系统在日志中记录警告，提示后续结果需要人工复核。若解析路径失败，系统通过重试或其他解析方式继续处理；如果最终无法获得有效文本，则返回错误信息并终止本次分析。

该设计将“文件可读性问题”与“合同风险判断问题”分离，使后续模块不需要关心输入来自文字层、OCR 还是其他文档转换路径。

### 4.2 合同类型与条款结构解析

结构解析模块将合同全文发送给模型，并要求模型以结构化 JSON 返回合同类型和条款列表。条款结构包括以下字段：

```json
{
  "id": "3.2",
  "type": "payment",
  "title": "付款条件",
  "text": "甲方应于验收后九十日内付款……",
  "relevance": ["equity", "financial"]
}
```

系统对模型返回内容进行结构化校验。当模型输出格式不符合预期时，系统尝试进行 JSON 解析和字段补全；如果结构解析仍然失败，则以合同类型提示或“其他”作为默认类型，并将全文的一部分作为待复核条款继续后续流程。该降级策略能够避免格式错误直接导致服务崩溃，但其输出质量需要在测试中单独评估。

### 4.3 知识库与法规资料检索

知识库模块保存合同风险规则和法规资料，并支持关键词匹配与向量检索。系统在 Stage 1 完成后，根据合同全文和合同类型检索相关规则与法规条文，再将检索结果作为参考信息注入风险 Worker 的输入。

知识库内容在模型分析中起到参考作用，而不是直接替代人工制定的风险标准。对于检索超时或检索失败的情况，系统跳过知识增强，继续执行风险分析。论文中不能将知识库检索结果默认视为正确法律结论，相关法律依据仍需要专业人员核对。

### 4.4 五维风险 Worker

#### 4.4.1 权责对等 Worker

该 Worker 关注双方义务是否对等、是否存在单方面解除权或变更权、通知义务是否平衡以及免责条款是否明显偏向一方。

#### 4.4.2 财务风险 Worker

该 Worker 关注付款周期、违约金、滞纳金、赔偿上限和预付款等内容。对于代码中使用的时间、比例和金额阈值，需要在正式论文中补充来源或将其明确表述为系统规则，而不能直接表述为普遍适用的法律标准。

#### 4.4.3 知识产权 Worker

该 Worker 关注工作成果归属、保密义务、竞业限制和数据使用权限等内容。

#### 4.4.4 争议解决 Worker

该 Worker 关注管辖地、仲裁条款、诉讼成本和举证责任等内容。

#### 4.4.5 通用风险 Worker

该 Worker 负责处理无法归入前述维度的内容，包括不可抗力、合同变更、合同转让、通知方式及其他可能影响合同履行的条款。

每个 Worker 使用统一的输出格式，包含 `risk_level`、`risk_type`、`issue`、`unfavorable_to`、`severity`、`suggestion` 和 `legal_basis` 等字段。统一字段便于不同 Worker 的结果合并和前端渲染。

### 4.5 冲突检测与二次分析

系统按照条款编号聚合 Worker 结果，并检查同一条款是否存在不同风险等级。当同一条款同时出现红色和绿色评级时，系统将该条款标记为冲突条款，并把各维度的分析摘要重新注入二次分析请求。二次分析的目标不是简单采用最高风险等级，而是让模型参考已有意见后重新给出风险判断。

需要指出的是，当前实现中的冲突检测主要覆盖红色与绿色之间的明显冲突，黄色与红色、黄色与绿色之间的差异仍需要进一步细化。正式版本还应记录复核前后的评级变化和复核原因，以便后续进行可追溯评估。

### 4.6 结果聚合与前端展示

结果聚合模块根据 Worker 输出生成红、黄、绿风险分布、综合分数、处理建议和最高风险条款。前端以条款列表和风险颜色展示结果，并提供原文查看、风险说明、修改建议和人工复核标记。

系统将“风险等级”“问题说明”和“修改建议”分开保存。这样用户可以区分模型对条款的判断、判断理由以及可能的协商方向，减少只显示单一颜色标签造成的信息损失。

### 4.7 异常处理与数据存储

系统在文档解析、模型调用、知识库检索和结果聚合等环节设置了重试、超时和降级逻辑。LLM 调用通过统一网关完成，网关负责模型配置、结构化输出、重试和响应信息记录。合同、分析结果、条款风险和知识规则通过 SQLAlchemy 写入 SQLite 数据库。

异常处理应区分“低风险”和“未完成分析”两种状态。若某个 Worker 调用失败，系统不应把该条款直接判定为绿色，而应使用未知状态或人工复核状态。该点属于系统安全性和论文可信度的重要改进项。

## 6 讨论

### 6.1 系统特点

ClauseLight 将合同风险审查拆分为多个明确阶段，使系统能够在文档解析、条款结构化、风险分析和结果聚合等位置分别记录状态。与直接进行整份合同问答相比，多阶段设计有利于把模型输入限制在特定任务范围内，也便于后续替换单个风险维度的 Prompt、规则或模型。

系统同时采用并行分析和人工复核标记。并行分析用于组织不同风险维度，人工复核标记则用于提示用户关注不同维度之间存在差异的条款。这种设计并不意味着模型能够自动解决所有冲突，而是将冲突显式暴露给用户。

### 6.2 系统局限

第一，系统输出依赖大语言模型，模型版本、提示词、上下文和温度变化都可能影响结果。第二，红黄绿风险等级和综合分数仍需要更明确的规则、数据集和人工标注进行校准。第三，法律依据和行业惯例的识别具有专业门槛，知识库内容需要持续维护并由专业人员核验。第四，当前项目的案例样本和长期运行数据有限，不能据此推断普遍适用性。第五，系统虽然能够给出风险提示和协商方向，但不应被用于替代律师或作出正式法律结论。

### 6.3 后续改进方向

后续工作可以从四个方面展开：一是建立经过脱敏和授权的合同数据集，制定条款和风险等级标注规范；二是引入法律背景人员参与标注和复核，提升风险依据的可信度；三是将冲突复核从固定流程扩展为可解释的规则与模型结合机制；四是对不同模型、本地模型和规则库配置进行对比测试，评估输出稳定性、延迟和成本。

## 7 结论

本文围绕非结构化合同风险辅助审查问题，设计并实现了基于多阶段 Agent 的 ClauseLight 系统。系统通过文档解析、条款结构化、五维风险并行分析、冲突检测和结果聚合，将合同审查任务组织为一条可观察、可扩展的处理流程，并通过本地数据库和统一模型网关提供工程支撑。

本文的主要价值在于完成了一个面向实际使用场景的合同风险辅助审查系统设计与实现，并对模型调用失败、知识检索失败和人工复核等工程问题进行了考虑。系统输出仍属于辅助信息，最终合同判断需要结合合同完整内容、适用法律和专业人员意见。后续需要通过更规范的数据集、人工标注和对比测试，进一步验证系统的稳定性和适用范围。
