# 基于多阶段 Agent 的合同风险辅助审查系统设计与实现

**English Title:** Design and Implementation of a Contract Risk Auxiliary Review System Based on a Multi-stage Agent Pipeline

## 摘要

针对 PDF、扫描图片等非结构化合同材料审查成本高、普通用户难以定位具体风险条款的问题，本文设计并实现合同风险辅助审查系统 ClauseLight。系统采用“文档解析—条款结构化—多维度风险分析—结果聚合”的多阶段 Agent 架构。文档入口负责从 PDF、图片或文本文件中提取合同正文；结构解析阶段识别合同类型并拆分条款；风险分析阶段将条款分配给权责对等、财务风险、知识产权、争议解决和通用风险五个 Worker 并行处理；聚合阶段生成综合分数、风险分布、修改建议和人工复核标记。系统后端采用 Python 与 FastAPI 实现，使用 SQLite 保存本地数据，并通过统一模型网关接入兼容 OpenAI 接口的远程模型或本地模型。

本文重点介绍系统需求、总体架构、关键模块和工程实现，并通过功能测试、本地运行记录和脱敏租赁合同案例验证主流程。测试结果表明，ClauseLight 能够完成合同接入、文本解析、条款级风险分析、结果保存和前端呈现。系统输出定位为签约前的辅助提示，不构成法律意见。

**关键词：** 合同风险审查；大语言模型；Agent；文档解析；OCR；多阶段流水线

## Abstract

To address the difficulty of quickly locating risky clauses in unstructured contract files such as PDFs and scanned images, this paper designs and implements ClauseLight, an auxiliary contract risk review system based on a multi-stage Agent pipeline. The system consists of document ingestion, clause structuring, multidimensional risk analysis, conflict review, and result aggregation. The ingestion module extracts text from PDFs, images, or text files; the structuring stage identifies the contract type and divides the document into clauses; five Workers analyze equity, financial, intellectual-property, dispute-resolution, and general risks in parallel; and the aggregation stage produces a risk distribution, an overall score, revision suggestions, and manual-review flags. The backend is implemented with Python and FastAPI, while SQLite is used for local persistence and a unified model gateway supports remote or local models. Functional tests, local execution records, and desensitized rental-contract cases are used to verify the completeness of the main workflow. The system provides auxiliary prompts for pre-signing review and does not constitute legal advice.

**Keywords:** contract risk review; large language model; Agent; document parsing; optical character recognition; multi-stage pipeline

## 1 引言

### 1.1 研究背景

合同是商业交易、劳动用工、房屋租赁和项目合作等活动中的重要法律文本。现实中的合同通常以 PDF、扫描图片或办公文档的形式保存，文本结构可能受到页面布局、扫描质量、字体和表格格式的影响。对于不具备法律专业背景的普通用户而言，在签署合同前快速识别付款周期、违约责任、单方面解除权、责任上限、知识产权归属和争议解决等条款中的潜在风险并不容易。

传统合同审查通常依赖人工逐条阅读，审查质量受人员经验、时间和合同长度影响。近年来，大语言模型在文本分类、信息抽取和自然语言生成方面表现出较强的通用能力，为合同条款解析和风险提示提供了新的技术路径。然而，直接将完整合同交给大语言模型进行一次性分析仍存在三个问题：一是长文本可能导致关键信息遗漏；二是不同风险类型混杂在同一次推理中，输出结构和判断标准不稳定；三是模型给出的结论不一定具有清晰的条款依据，难以支持用户复核。

基于上述问题，本文不把合同审查建模为单次问答，而是拆成多个可记录、可复核的处理阶段。系统先把非结构化文件转换为条款列表，再由不同风险维度的 Worker 分别处理，最终合并为条款级风险结果。这样做的目的很朴素：让系统知道自己分析到了哪一步，也让用户能回到原文核对模型判断。

### 1.2 研究内容

围绕合同风险辅助审查场景，本文完成了文档入口、合同结构解析、五维风险分析、冲突检测、结果聚合和本地化存储等模块的设计与实现。文档入口统一处理文字型 PDF、图片和文本文件，并根据解析质量选择文本层解析或 OCR 路径；结构解析模块将合同全文转换为合同类型、条款编号、标题、正文和风险维度关联关系；风险分析阶段将条款路由到五个 Worker 并行处理；结果模块保存风险等级、问题说明、修改建议和人工复核标记。文章还对模型调用、知识库检索、异常重试和降级路径进行了工程化组织。

本文结构如下：第 1 章介绍研究背景和研究内容；第 2 章说明相关技术、系统需求和设计目标；第 3 章说明总体架构和数据流程；第 4 章介绍关键模块实现；第 5 章给出功能测试、本地运行记录和案例分析；第 6 章讨论系统特点与局限；第 7 章总结全文。

## 2 需求分析与系统设计目标

### 2.1 相关技术与研究基础

大语言模型能够对合同文本进行分类、信息抽取和自然语言解释，但合同审查通常需要同时处理长文档、跨条款关系和证据定位问题。ContractNLI 将合同审查建模为文档级自然语言推理任务，要求系统判断假设与合同之间的蕴含、矛盾或未提及关系，并识别支持判断的证据片段[1]。这一研究路径说明，合同分析系统不能只输出整体标签，还应保留与具体条款相关的依据。

LexGLUE 将多个法律语言理解任务组织为统一基准，覆盖分类、检索、条文预测和推理等任务[2]。DocInfer 研究长文档中的证据选择问题，并在合同和其他法律文本数据集上讨论证据筛选对文档级推理的作用[3]。本文不复现这些基准任务，而是结合合同风险辅助审查场景，将条款结构化、风险维度分工和依据呈现组织为一套工程流程。

ReAct 研究了大语言模型推理过程与外部行动交替执行的方式[4]。本文不采用完全自主的 ReAct Agent，而是使用固定阶段的 Pipeline，仅在冲突条款复核时调用有限的知识和记忆工具。合同审查步骤相对明确，固定阶段更便于记录输入、输出和错误位置，也便于进行功能测试。

对于扫描合同和图片合同，OCR 是系统进入后续语义分析的前置环节。PP-OCR 研究了面向实际场景的轻量化 OCR 系统，涉及文本检测、方向处理、文本识别和计算效率之间的平衡[5]。本文将文字层解析与 OCR 组合为文档入口，并在文本不足或解析失败时提供降级路径。

### 2.2 功能需求

ClauseLight 的核心使用流程为：用户上传合同文件，系统完成文字识别和条款分析，最终返回风险提示和修改建议。根据该流程，系统需要满足以下功能需求。

#### 2.2.1 合同文件接入

系统应支持用户上传 PDF、图片等常见合同文件，并对文件类型和大小进行基本校验。对于包含文字层的 PDF，系统优先提取已有文本；对于扫描图片或文字提取结果不足的文件，系统调用 OCR 进行识别。解析结果应统一转换为后续模块可以处理的文本对象。

#### 2.2.2 合同结构解析

系统需要识别合同类型并拆分合同条款。每条条款至少包含条款编号、标题、正文、条款类型和相关风险维度等信息。结构化结果用于控制后续 Worker 的输入范围，减少无关文本对分析结果的干扰。

#### 2.2.3 多维度风险分析

系统将风险分析划分为五个维度：权责对等、财务风险、知识产权、争议解决和通用风险。每个维度关注不同的合同风险问题，并输出风险等级、风险类型、问题说明、不利方、严重程度、修改建议和相关依据等字段。

#### 2.2.4 结果聚合与展示

系统应对多个风险 Worker 的分析结果进行合并，统计红、黄、绿风险数量，生成综合风险分数和处理建议，并对存在不同评级的条款给出人工复核提示。前端应支持查看条款原文、风险说明、修改建议和相关法律资料。

#### 2.2.5 异常处理与本地存储

由于文档解析和大语言模型调用均可能失败，系统应提供重试、超时和降级处理。合同和分析结果默认保存在本地 SQLite 数据库中，避免将用户合同自动上传到额外的业务服务器。远程模型调用需要用户显式同意，未同意时上传接口不读取或保存待处理合同内容。[CODE-CONFIG-001]

### 2.3 非功能需求

（1）**可维护性。** 将文档解析、模型调用、条款解析、风险分析和结果聚合拆分为独立模块，便于替换模型或调整某一风险维度。

（2）**可解释性。** 系统输出应尽量绑定到具体条款，避免只返回无法追溯的总体分数。

（3）**可扩展性。** 风险维度、规则库和模型提供商应能够在不改变主要 API 的情况下扩展。

（4）**数据安全性。** API Key 不写入业务代码，合同正文不在日志中完整输出，用户可以选择本地模型或关闭同步功能。

（5）**降级可用性。** 某一解析路径、知识库检索或单个 Worker 失败时，系统应记录失败状态并尽可能保留人工复核所需的信息。

### 2.4 系统设计目标

系统设计目标包括三点：第一，将合同分析任务拆成可观察、可测试的处理阶段；第二，通过风险维度分工降低单次模型调用的任务复杂度；第三，将模型输出转为条款级风险提示，避免只给用户一个难以复核的整体结论。

## 3 系统总体设计

### 3.1 总体架构

ClauseLight 采用本地优先的客户端—服务端结构。用户可以通过管理面板上传合同文件，后端服务负责文档解析、模型调用、知识库检索和结果持久化，前端负责进度展示与结果渲染。系统主要由文档入口层、Agent 编排层、知识支撑层、数据存储层和结果展示层组成。

系统的基本数据流如图 1 所示。

```text
合同文件
   │
   ▼
文档解析与 OCR
   │
   ▼
合同类型识别与条款结构化
   │
   ├── 知识库与法规资料检索
   │
   ▼
五维风险 Worker 并行分析
   │
   ▼
冲突检测与二次复核
   │
   ▼
风险聚合、综合评分与建议
   │
   ▼
条款列表、原文标注和分析报告
```

后端主要使用 Python、FastAPI 和 SQLAlchemy 实现，SQLite 用于保存合同、分析结果、条款分析和知识规则等数据。大语言模型调用通过统一网关完成，以便适配不同的 OpenAI 兼容接口和本地 Ollama 模型。文档入口对 PDF 先尝试 AnyDoc，再检查 PyMuPDF 文本层，文本不足时进入 PaddleOCR；办公文档走 AnyDoc，图片走 PaddleOCR。

从模块职责看，文档入口层负责将文件转换为统一的 `DocumentResult`；Agent 编排层负责组织 Stage 1、Stage 2 和 Stage 3；风险分析层由五个 Worker 组成；知识支撑层提供规则和法规资料检索；数据层保存合同、条款、分析结果和知识对象；展示层负责将分析进度和条款级结果返回给用户。各层通过结构化对象传递数据，便于替换单个解析器、模型或风险维度。

### 3.2 多阶段 Agent 流程

系统不是一个完全自主的 ReAct Agent，而是以预定义 Pipeline 为主、以有限工具调用为辅。合同风险审查的处理步骤具有相对明确的顺序，因此使用固定阶段能够使输入、输出和错误位置更容易被记录。

#### 3.2.1 Stage 1：结构解析

Stage 1 接收文档入口输出的合同全文，调用大语言模型识别合同类型并拆分条款。每个条款包含编号、类型、标题、正文和相关风险维度。`relevance` 字段用于决定该条款是否需要被某个风险 Worker 分析。

#### 3.2.2 Stage 2：并行风险分析

Stage 2 根据条款的风险维度关联关系组织五个 Worker。各 Worker 接收与自身维度相关的条款，并按照统一结构输出分析结果。系统使用异步任务并行执行不同维度的分析请求，再合并各 Worker 的结果。

#### 3.2.3 冲突复核

同一条款可能同时属于多个风险维度。例如，责任限制条款既可能涉及权责对等，也可能涉及财务风险。当同一条款出现红色和绿色评级时，系统将其标记为冲突，并触发包含其他维度意见的二次分析。冲突条款同时保留人工复核标记。

#### 3.2.4 Stage 3：结果聚合

Stage 3 接收所有 Worker 的结果，统计风险分布，生成综合风险分数、最高风险条款、简要总结和处理建议。聚合结果最终与条款结构信息合并，供前端按风险等级展示。

### 3.3 核心数据对象

系统内部主要使用以下数据对象：

（1）**DocumentResult。** 保存全文、页面信息、来源路径和平均解析置信度。

（2）**ClauseItem。** 保存条款编号、类型、标题、正文和相关风险维度。

（3）**ClauseRisk。** 保存条款风险等级、风险类型、问题说明、不利方、严重程度、修改建议和法律依据。

（4）**AnalysisResult。** 保存合同类型、综合分数、风险分布、最高风险、人工复核条款和条款级最终结果。

（5）**KnowledgeRule 与 LegalReference。** 保存可供检索的规则、法规名称、条文编号和条文内容。

### 3.4 数据库与接口设计

系统使用 SQLAlchemy 映射本地 SQLite 数据库。`contracts` 保存合同文件的基本信息和解析状态，`analyses` 保存一次合同分析任务的类型、评分、风险分布和处理建议，`clause_analyses` 保存条款级风险结果，`knowledge_rules` 和 `legal_references` 分别保存风险规则与法规资料。记忆相关表用于记录 Agent 的会话、事件和知识片段，但这些记录仅作为系统运行痕迹，不作为合同风险识别效果数据。

一次分析请求通常经过以下接口流程：用户上传文件后，系统创建合同记录并返回任务标识；文档入口完成解析后，后端通过 SSE 推送当前阶段和进度；分析结束后，系统保存 `AnalysisResult` 及条款级结果；前端通过合同详情和分析结果接口查询综合评分、风险分布、原文标注、修改建议和人工复核标记。WebSocket 仅用于实际存在的辅助连接链路。若任一阶段失败，接口应返回失败信息或待复核状态，不能把未完成分析直接解释为低风险。

## 4 关键模块设计与实现

### 4.1 文档解析与 OCR 降级

文档解析模块通过统一的 `ingest` 接口接收文件路径，并根据文件类型和已有文本质量选择处理路线。对文字型 PDF，系统优先使用文本层解析；当文本层不足或文件为图片时，系统转入 OCR 路径。OCR 结果包含全文、页面、文本块和置信度等信息。

系统在解析完成后检查全文是否为空，并记录平均置信度。当置信度低于设定阈值时，系统在日志中记录警告，提示后续结果需要人工复核。若解析路径失败，系统通过重试或其他解析方式继续处理；如果最终无法获得有效文本，则返回错误信息并终止本次分析。

该设计将“文件可读性问题”与“合同风险判断问题”分离，使后续模块不需要关心输入来自文字层、OCR 还是其他文档转换路径。

### 4.2 合同类型与条款结构解析

结构解析模块将合同全文发送给模型，并要求模型以结构化 JSON 返回合同类型和条款列表。条款结构包括以下字段：

```json
{
  "id": "3.2",
  "type": "payment",
  "title": "付款条件",
  "text": "甲方应于验收后九十日内付款……",
  "relevance": ["equity", "financial"]
}
```

系统对模型返回内容进行结构化校验。当模型输出格式不符合预期时，系统尝试进行 JSON 解析和字段补全；如果结构解析仍然失败，则以合同类型提示或“其他”作为默认类型，并将全文的一部分作为待复核条款继续后续流程。该降级策略能够避免格式错误直接导致服务崩溃，但其输出质量需要在测试中单独评估。

### 4.3 知识库与法规资料检索

知识库模块保存合同风险规则和法规资料，并支持关键词匹配与向量检索。系统在 Stage 1 完成后，根据合同全文和合同类型检索相关规则与法规条文，再将检索结果作为参考信息注入风险 Worker 的输入。

知识库内容在模型分析中起到参考作用，而不是直接替代人工制定的风险标准。对于检索超时或检索失败的情况，系统跳过知识增强，继续执行风险分析。论文中不能将知识库检索结果默认视为正确法律结论，相关法律依据仍需要专业人员核对。

### 4.4 五维风险 Worker

#### 4.4.1 权责对等 Worker

该 Worker 关注双方义务是否对等、是否存在单方面解除权或变更权、通知义务是否平衡以及免责条款是否明显偏向一方。

#### 4.4.2 财务风险 Worker

该 Worker 关注付款周期、违约金、滞纳金、赔偿上限和预付款等内容。系统中涉及时间、比例和金额的阈值被定义为辅助审查规则，用于提示用户关注可能需要协商的条款，不被表述为普遍适用的法律标准。

#### 4.4.3 知识产权 Worker

该 Worker 关注工作成果归属、保密义务、竞业限制和数据使用权限等内容。

#### 4.4.4 争议解决 Worker

该 Worker 关注管辖地、仲裁条款、诉讼成本和举证责任等内容。

#### 4.4.5 通用风险 Worker

该 Worker 负责处理无法归入前述维度的内容，包括不可抗力、合同变更、合同转让、通知方式及其他可能影响合同履行的条款。

每个 Worker 使用统一的输出格式，包含 `risk_level`、`risk_type`、`issue`、`unfavorable_to`、`severity`、`suggestion` 和 `legal_basis` 等字段。统一字段便于不同 Worker 的结果合并和前端渲染。

### 4.5 冲突检测与二次分析

系统按照条款编号聚合 Worker 结果，并检查同一条款是否存在不同风险等级。当同一条款同时出现红色和绿色评级时，系统将该条款标记为冲突条款，并把各维度的分析摘要重新注入二次分析请求。二次分析的目标不是简单采用最高风险等级，而是让模型参考已有意见后重新给出风险判断。

当前实现中的冲突检测主要覆盖红色与绿色之间的明显冲突。黄色与红色、黄色与绿色之间的差异没有全部触发二次分析，而是保留在条款级结果中供用户查看。这一取舍降低了系统复杂度，但也意味着系统更适合做签约前的风险提示，而不是自动形成最终法律判断。

### 4.6 结果聚合与前端展示

结果聚合模块根据 Worker 输出生成红、黄、绿风险分布、综合分数、处理建议和最高风险条款。前端以条款列表和风险颜色展示结果，并提供原文查看、风险说明、修改建议和人工复核标记。

系统将“风险等级”“问题说明”和“修改建议”分开保存。这样用户可以区分模型对条款的判断、判断理由以及可能的协商方向，减少只显示单一颜色标签造成的信息损失。

### 4.7 异常处理与数据存储

系统在文档解析、模型调用、知识库检索和结果聚合等环节设置了重试、超时和降级逻辑。LLM 调用通过统一网关完成，网关负责模型配置、结构化输出、重试和响应信息记录。合同、分析结果、条款风险和知识规则通过 SQLAlchemy 写入 SQLite 数据库。

异常处理应区分“低风险”和“未完成分析”两种状态。若某个 Worker 调用失败，系统不应把该条款直接判定为绿色，而应使用未知状态或人工复核状态。该点属于系统安全性和论文可信度的重要改进项。

案例分析使用已授权用于论文写作的租赁合同样本。为避免泄露隐私，论文不展示姓名、手机号、身份证号、详细地址、银行账号等内容，只保留条款类型、风险类型和处理结果。案例分析的目的，是展示 ClauseLight 如何把合同文件转换为条款级风险提示，而不是证明系统可以替代法律专业人员审查。

#### 5.4.1 含风险条款的租赁合同案例

案例 A 为一份两页租赁合同 PDF，文字层约 1425 个字符。合同包含租金支付、押金处理、维修责任、转租限制、出租方单方解除、违约责任和争议解决等条款。系统完成解析后，将合同拆分为若干条款，并在财务风险、权责对等、争议解决等维度上生成条款级结果。

系统保存的该案例综合分数为 35，处理建议为“协商后再签”。红色风险主要集中在三类条款：一是押金扣除或不退还条件表述宽泛，承租人难以预估责任范围；二是逾期付款、违约金或占用费条款对承租人负担较重；三是出租方单方解除或提前收回房屋的条件较宽，双方解除权不够对等。黄色风险主要涉及维修责任边界、通知方式和费用承担。绿色结果多为租赁期限、基础身份信息等风险较低的条款。

该案例说明，多阶段 Agent 流程能够把一份普通租赁合同转换为可阅读的风险列表。用户在界面中可以先查看综合分数，再展开具体条款，看到风险原因和修改建议。与只给出“合同有风险”的整体提示相比，条款级输出更便于用户定位原文，也便于后续交给专业人员复核。

#### 5.4.2 E2E 租赁合同案例

案例 B 为另一份两页租赁合同 PDF，文字层约 1550 个字符；同时保留一份对应 TXT 文本，约 1594 个字符。PDF 与 TXT 输入用于观察不同入口形式下的主流程表现。该合同覆盖租赁期限、租金支付、押金返还、维修责任、转租限制、出租方单方收回、费用承担、免责条款和争议解决等内容。

系统对该类样本保存了多次分析结果，综合分数分布在 18 至 30 之间，处理建议为“拒绝”或“先协商”。条款级结果显示，系统能够识别出单方解除权不对等、押金没收条件、违约金或占用费偏高、维修义务与免责条款失衡、管辖地及诉讼成本分担等问题。这些结果与租赁合同审查中常见的关注点基本一致。

## 6 讨论

### 6.1 系统特点

ClauseLight 的主要特点是把合同风险审查拆分为多个明确阶段，使系统能够在文档解析、条款结构化、风险分析和结果聚合等位置分别记录状态。与直接进行整份合同问答相比，多阶段设计可以把模型输入限制在特定任务范围内，也便于后续替换单个风险维度的 Prompt、规则或模型。

系统同时采用并行分析和人工复核标记。并行分析用于组织不同风险维度，人工复核标记用于提示用户关注不同维度之间存在差异的条款。这种设计不假设模型能够自动解决所有冲突，而是把冲突显式暴露出来。对于合同这种高风险文本，这一点比单纯追求自动化更重要。

系统的另一个特点是保留本地优先的工程形态。合同文本和分析结果默认存入本地 SQLite 数据库，远程模型是否启用由用户配置控制。对于个人用户和小型团队，这种设计降低了部署门槛，也避免把所有合同材料绑定到单一云端服务。

### 6.2 系统局限

系统仍存在明显局限。第一，输出依赖大语言模型，模型版本、提示词、上下文长度和温度变化都可能影响结果。第二，红黄绿风险等级和综合分数仍属于系统规则，需要更多人工标注数据校准。第三，法律依据和行业惯例的识别具有专业门槛，知识库内容需要持续维护并由专业人员核验。第四，当前案例样本和长期运行数据有限，不能据此推断系统在所有合同类型上的效果。第五，系统虽然能够给出风险提示和协商方向，但不能替代律师，也不能单独作为签约或诉讼决策依据。

工程实现上仍有需要改进的地方。当前 Worker 调用失败、结构解析失败或引用校验失败时使用 `unknown`/“待复核”状态，并在前端用独立样式展示；冲突检测主要处理红色与绿色之间的明显冲突，黄色等级变化仍需人工判断。系统保留初始结果、冲突复核结果和多 Worker 轨迹，便于后续记录人工复核结论。[TEST-FAILURE-001]

### 6.3 后续改进方向

后续工作可以从四个方面展开。第一，建立经过脱敏和授权的合同数据集，制定条款拆分、风险等级和修改建议的标注规范。第二，引入法律背景人员参与标注和复核，形成可复用的风险判断标准。第三，将冲突复核从固定流程扩展为规则与模型结合的机制，使系统能够解释为什么选择某一风险等级。第四，对不同模型、本地模型和规则库配置进行对比测试，记录输出稳定性、运行延迟和调用成本。

## 7 结论

本文围绕非结构化合同风险辅助审查问题，设计并实现了基于多阶段 Agent 的 ClauseLight 系统。系统通过文档解析、条款结构化、五维风险并行分析、冲突检测和结果聚合，将合同审查任务组织为一条可观察、可扩展的处理流程，并通过本地数据库和统一模型网关提供工程支撑；远程模型处理要求用户显式授权，法规引用受数据库 ID 和来源记录约束。[CODE-CONFIG-001][LAW-SOURCE-001]

测试和案例分析表明，该系统能够完成合同文件接入、文本解析、条款级风险分析、结果保存和前端展示等流程。本地运行记录中保存了 10 条合同记录、7 条分析记录和 92 条条款分析记录；全量测试结果为 313 个通过、2 个跳过、8 个警告，路线 B 指定模块覆盖率为 72.49% 且未达门禁。这些结果支持本文关于系统工程可行性的判断，但不支持法律判断准确率结论。[TEST-BASELINE-001][TEST-COVERAGE-001]

ClauseLight 的定位是合同风险辅助审查工具。它适合帮助用户在签约前快速发现需要关注的条款，并把风险原因和修改建议组织成可复核的形式。对于法律效力判断、争议处理和最终签约决策，仍需要结合完整合同、适用法律和专业人员意见。后续研究将围绕脱敏数据集、人工标注、模型对比和冲突复核机制继续完善。
