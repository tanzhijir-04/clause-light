# ClauseLight ContractOps 2.0 Delivery Roadmap

**目标：** 在 `dev/2.0` 分支上把 ClauseLight 演进为企业通用合同全生命周期智能底座，并让每个模块都能独立运行、测试、演示和量化。

**设计依据：** `docs/superpowers/specs/2026-09-09-contractops-2.0-design.md`

## 1. 交付策略

- 按 M0–M7 串行推进，任一模块未通过发布门时不启动下一个业务模块。
- M0–M1 优先形成求职所需的生产级 AI 应用证据；M2–M7 扩展企业合同生命周期。
- 每个模块单独编写实施计划、测试清单和 ADR，并在独立提交中落地。
- v1 代码在 M1 验收前保留；2.0 使用 `/api/v2` 和新数据库迁移，不原地篡改用户的 v1 SQLite。
- PostgreSQL 始终是事实源；Redis 是可关闭的加速层；Kafka 直到 M5 才成为运行组件。

## 2. 模块依赖

```text
M0 合同智能底座
  |
  +--> M1 签前智能审查 / RAG
         |
         +--> M2 谈判与修订
                |
                +--> M3 审批与签署
                       |
                       +--> M4 履约义务
                              |
                              +--> M5 履约事件与风险处置（Kafka）
                                     |
                                     +--> M6 续约与终止

M0 -----------------------------------------------> M7 企业治理与集成

Eval / Tracing / Reliability / Security 贯穿所有模块
```

## 3. M0：合同智能底座

**业务结果：** 企业用户可以在租户边界内导入合同，创建不可变版本，提交可恢复的处理任务，并查看完整进度和审计记录。

**主要交付：**

- PostgreSQL + SQLAlchemy 2.0 + Alembic；
- 企业、用户、成员、API 凭据、合同、版本、合同主体、稳定条款、文件资产；
- `ProcessingJob`、`JobStep`、事务 Outbox；
- Redis 限流、缓存和进度广播，开发环境可降级；
- `/api/v2`、请求 ID、结构化日志、OpenTelemetry、Prometheus 指标；
- PaddleOCR 兼容版本锁定和真实图片冒烟测试；
- v1 SQLite 只读幂等导入器；
- API、Worker、PostgreSQL、Redis 的 Docker Compose；
- GitHub Actions 单元、集成、迁移和静态检查。

**发布门：**

- 空 PostgreSQL 能从 Alembic `upgrade head` 启动；
- 同一个幂等键不会产生两个合同版本或两个副作用；
- Worker 中断后可从最后完成步骤继续；
- Redis 故障不会丢失最终任务状态；
- 跨租户读写测试全部拒绝；
- v1 导入前后逐类计数一致，重复导入不重复写入；
- OCR 对固定样例产生非空文本；
- Docker Compose 健康检查和 CI 全绿。

**实施计划：** `docs/superpowers/plans/2026-09-09-contractops-2.0-m0-foundation.md`

## 4. M1：签前智能审查与生产级 RAG

**业务结果：** 用户上传合同后获得带精确出处、可信度和人工复核状态的风险结论，并能解释检索和模型为什么产生该结论。

**主要交付：**

- 法规、企业制度、标准条款和历史合同的统一知识摄取；
- PostgreSQL 全文检索 + pgvector + Reciprocal Rank Fusion；
- Cross-encoder Rerank、Query Rewrite、语义完整 Chunking；
- ACL 过滤、去重、排序、Token Budget 和 Context Package；
- 任务分解、工具 schema、超时、重试、Fallback 和 HITL；
- 模型路由、Prompt 压缩、Token/成本记录和预算告警；
- 固定 RAG 评测集与 Recall@K、MRR、引用正确率、无依据结论率；
- 检索 Trace、模型 Trace 和审查结果页面。

**发布门：**

- 测试集 ACL 泄漏为 0；
- 混合检索相对单一路径的指标由实验报告自动计算；
- Rerank 增益、P95 时延和单合同成本可复现；
- 每个风险结论至少有一个有效 Citation，否则进入人工复核；
- 主模型、Embedding 或 Reranker 故障时产生明确降级状态，不伪装成功。

**求职证据：** 完整 RAG、复杂 Agent、模型路由、成本意识和 Eval-driven Development。

## 5. M2：谈判与修订

**业务结果：** 法务和业务可以围绕条款差异协作，生成修订建议，保留采纳/拒绝理由，并形成新的不可变合同版本。

**主要交付：**

- 条款级 Diff 和语义变更分类；
- 风险结论到修订建议的可追溯映射；
- `NegotiationMatter`、`RevisionProposal`、`CommentThread`；
- Word 修订导出和版本对比页面；
- 采用、拒绝、人工改写的反馈事件；
- 修订前后风险变化和采纳率指标。

**发布门：**

- 每条修订均指向源版本、目标条款和生成依据；
- 接受修订只创建新版本，不覆盖旧版本；
- 并发编辑冲突可检测；
- 导出文件和系统内 Diff 一致；
- 修订采纳率与误改率能由审计数据计算。

## 6. M3：审批与签署

**业务结果：** 合同按金额、风险、类型和组织规则进入可恢复的审批流，并通过统一适配器衔接电子签署。

**主要交付：**

- 条件审批模板和状态机；
- 会签、或签、退回、撤回、超时和升级；
- 高风险条款强制人工确认；
- 电子签 `SignatureProvider` 接口和本地模拟器；
- 审批 SLA 和瓶颈指标；
- `contract.approved`、`signature.completed` Outbox 事件。

**发布门：**

- 状态迁移表覆盖所有允许和禁止路径；
- Worker 重启不重复发送审批或签署请求；
- 所有决定包含操作者、时间、理由和版本；
- 外部签署超时或回调重复时保持幂等。

## 7. M4：履约义务

**业务结果：** 系统把已签合同转成可跟踪的付款、交付、验收、保密和通知义务，并要求负责人提交履约证据。

**主要交付：**

- 义务、责任方、相对方、期限、触发条件和证据要求抽取；
- 义务人工确认工作台；
- 里程碑、提醒、证据附件和状态变更；
- 义务到原始条款和合同版本的双向追溯；
- 逾期、缺证据和依赖阻塞规则；
- `obligation.created`、`obligation.due`、`obligation.overdue` 事件。

**发布门：**

- 未经人工确认的低置信度义务不会自动产生外部动作；
- 日期、金额和责任方冲突进入复核队列；
- 证据和状态变化拥有不可变审计记录；
- 固定样例上的义务召回率和字段准确率可复现。

## 8. M5：履约事件与风险处置

**业务结果：** ERP、财务、工单或人工事件进入统一生命周期事件流，系统关联合同义务、识别风险并执行可审计 Playbook。

**主要交付：**

- Kafka 事件信封、版本和 Schema Compatibility；
- PostgreSQL Outbox Relay；
- 幂等消费者、重试、Dead Letter 和安全重放；
- 事件到合同/义务的实体解析；
- 风险信号聚合、处置 Playbook 和 HITL；
- Lag、失败率、重复率和恢复时间指标。

**发布门：**

- Outbox 与业务写入同一事务；
- 重复事件不产生重复副作用；
- 消费者崩溃、网络分区和错误 schema 经故障注入验证；
- DLQ 事件可以在修复后按 ID 安全重放；
- Kafka 停止时 M0–M4 核心读写仍可用。

**求职证据：** Kafka 的价值来自真实履约事件和可靠性验证，而不是技术栈占位。

## 9. M6：续约与终止

**业务结果：** 系统识别续约窗口、自动续约和终止条件，在法定或约定期限前生成需要人工确认的通知动作。

**主要交付：**

- 续约窗口、通知期、终止权和违约退出条件；
- 日历视图和多级提醒；
- 终止/续约影响分析；
- 通知文本生成、审批和发送适配器；
- 漏提醒、按时处置和节约金额指标。

**发布门：**

- 所有日期计算保留原始条款、时区和计算过程；
- 通知发送必须经过人工确认；
- 重复调度不会重复通知；
- 临界日期和节假日规则拥有参数化测试。

## 10. M7：企业治理与集成

**业务结果：** 系统可以按企业组织、角色、制度、保留策略和外部连接器进行规模化治理。

**主要交付：**

- RBAC 与资源级授权；
- SSO/OIDC 适配层；
- 数据保留、删除审批、导出和法律保全；
- ERP、CRM、采购、文档库和消息平台连接器框架；
- 组织级规则版本和灰度发布；
- 管理看板、审计导出和成本预算。

**发布门：**

- 权限矩阵和跨租户隔离测试全绿；
- 删除、保留和法律保全规则无冲突；
- 连接器凭据加密且不进入日志；
- 组织级成本、质量和效率指标可追溯到原始事件。

## 11. 横切工作流

每个模块必须同时完成以下工作，不能在项目末尾集中补做：

1. 先写失败测试，再写最小实现；
2. 为 schema、API、状态机和事件契约写兼容性测试；
3. 为外部依赖写超时、重试、降级和故障注入测试；
4. 更新架构决策、API 文档和运行手册；
5. 生成固定格式的性能、质量、成本报告；
6. 完成一个可独立回滚的中文 gitmoji 提交；
7. 不自动 push，由用户决定何时推送。

## 12. 简历与面试交付物

| 阶段 | 可展示内容 |
| --- | --- |
| M0 | PostgreSQL/Alembic、Redis 限流与进度、持久任务、Outbox、可观测、Docker/CI、迁移可靠性 |
| M1 | Hybrid Search、Rerank、Context Engineering、Agent 恢复、模型路由、质量/成本量化 |
| M2–M4 | 合同版本、谈判协作、审批状态机、履约义务抽取与 HITL |
| M5–M7 | Kafka 可靠事件、企业集成、RBAC、治理与跨系统交付 |

面试讲述顺序固定为：业务问题 → 约束 → 选型对比 → 架构 → 故障与安全 → 量化结果。只有实验报告生成的数据才能进入简历。
